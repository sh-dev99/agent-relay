# Codex の受信箱を子エージェントで見張った検証記録

通常の送信には [Codex の宛先と送信方法](codex.md) を使う。ここでは、2026-11-16 までに試した旧方式について、後から挙動を確認するために記録を残す。

## 分かったこと

専任の子エージェントが受信フォルダを監視し、親エージェントへメッセージを渡す方法を試した。親のターンが終了した後に子が通知しても、親が自動で再開するとは限らなかった。別途キューにメッセージを入れて親が再開するまで、通知が処理されなかった例がある。`collaboration.send_message` 自体に、新しいターンを始める機能はない。

受信フォルダにファイルができたこと、子が拾ったこと、親が読んだことはそれぞれ別の段階。親が読んだかどうかは、親からの返事で確かめた。親が動いていない状態から起こす用途には、現在の送信手順を参照する。

## 当時の構成

同じ Mac に送信側と専任の子がアクセスできる専用フォルダを作り、子は `scripts/codex_inbox.py watch` でファイルを監視した。親はターンを終えず、`collaboration.wait_agent` などで通知を待った。待機中も子エージェントを1人使う。中断、利用上限、アプリ終了、スリープ後に同じように動くかは確認できていない。

送信側が `scripts/codex_inbox.py send` で本文を渡すと、受信フォルダに `.msg` が置かれる。送信側の標準出力は拡張子を除いた ID、監視側の JSON の `id` は `.msg` を含むファイル名。照合するときは拡張子の有無を揃える。書き込み途中の `.tmp` は監視の対象外で、既存の `.msg` は上書きせず使っていた。

子は送り主を添えて親に渡し、親が処理を確認するまでファイルを残した。監視プロセスを再起動すると残っているファイルが再出力される可能性があるため、ID で処理済みかを照合した。復旧時に結果が分からない文は、到達確認が取れるまで再送を控えた。

## 終了時に行ったこと

送信側に終了を知らせ、子が自分で起動した監視プロセスを停止した。未処理の文や結果不明の文を確認してから、この検証用に作った受信フォルダだけを片づけた。
